category: 貪欲法
subcategory: 基本貪欲法
complexity: O(n log n)
summary: サイズの異なる複数のソート済みファイルを2つずつマージしていくとき、常に最小サイズの2つを選んで結合する貪欲法が、総比較回数(総マージコスト)を最小化する結合順序を与える。

## 概要

複数のソート済みファイル(あるいは配列)を1つの大きなソート済みファイルにまとめたいとき、一度に2つのファイルしかマージできない(2-wayマージ)という制約のもとでは、「どの順番でどの2つを組み合わせるか」によって、必要な総比較回数(処理コスト)が大きく変わる。たとえばサイズ`20, 30, 10`の3つのファイルをマージするなら、先に小さい2つ(`10`と`20`)を結合してから残り(`30`)と結合する方が、先に`20`と`30`を結合してから`10`と結合するより総コストが少なくなる。

最適マージパターンは、「**常に現時点で最小サイズの2つのファイル(またはマージ済みの塊)を選んで結合する**」という貪欲法で、総マージコスト(2つのファイルをマージするコストは、それぞれのサイズの和とみなす)を最小化する結合順序を求める手法である。この貪欲戦略は、[ハフマン符号化](/algorithms/huffman-coding)が「最も頻度の低い2つの記号(ノード)を繰り返し結合する」のと全く同じ構造を持っており、実際に最適マージパターンの問題はハフマン符号木の構築と数学的に同一の問題として扱える。

## 仕組み

1. 全てのファイルのサイズを、優先度付きキュー(最小ヒープ)に投入する
2. ヒューから最小サイズの2つの値`a`, `b`を取り出す
3. `a + b`を今回のマージのコストとして総コストに加算し、`a + b`を新しい塊のサイズとしてヒープに戻す
4. ヒープに要素が1つになるまで、2〜3を繰り返す
5. 積み上げた総コストが、この結合順序全体の最小マージコストになる

これは[ハフマン符号化](/algorithms/huffman-coding)の木構築アルゴリズムと一字一句同じ手続きであり、「ファイルサイズ」を「記号の出現頻度」に置き換えれば、そのまま同じ貪欲法になる。結合の様子を二分木として描くと、サイズの小さいファイルほど木の深い位置(=多くの回数マージに巻き込まれる)に配置され、サイズの大きいファイルほど浅い位置(=マージされる回数が少ない)に配置される。これはハフマン木において頻度の低い記号ほど長い符号(深い葉)を持つことと対応している。

**具体例で追う**: サイズ`{20, 30, 10, 5, 30}`の5つのファイルを考える。

| 手順 | ヒープの中身(処理前) | 選んだ2つ | マージ後のサイズ | このマージのコスト | 累積コスト |
|---|---|---|---|---|---|
| 1 | `5, 10, 20, 30, 30` | `5, 10` | `15` | `15` | `15` |
| 2 | `15, 20, 30, 30` | `15, 20` | `35` | `35` | `50` |
| 3 | `30, 30, 35` | `30, 30` | `60` | `60` | `110` |
| 4 | `35, 60` | `35, 60` | `95` | `95` | `205` |

最終的な総マージコストは`205`になる。もし逆に「サイズの大きい2つを先に結合する」戦略(`30, 30`→`5, 10`→`20, 60`→…)を取ると、大きな塊が何度も再結合に巻き込まれるため総コストはこれより明らかに大きくなる。「小さいものを先に沈めて深い位置に固定し、大きいものを浅い位置に留める」という直感が、そのまま最小コストにつながっていることがこの表からも確認できる。

## 特性・トレードオフ

- **貪欲法が最適である理由**: あるファイルが結合される回数(木の深さ)はそのマージコストへの寄与回数に等しいため、総コストは「各ファイルのサイズ × そのファイルが巻き込まれるマージ回数(木の深さ)」の総和になる。最小サイズの2つを最初に結合すれば、それらは(他の任意の組み合わせと比べて)最も深い位置に配置されることになり、サイズの大きい方をなるべく浅い位置に留めることができる。これは交換論法で「最小の2つを先に結合しない解は、常に最小の2つを先に結合する解で改善できる」ことを示せるため、貪欲法の最適性が証明できる
- **ハフマン符号化との等価性**: 最適マージパターン問題とハフマン符号木構築問題は、数学的には全く同じ問題である。「ファイルサイズを最小化する結合順序」と「記号の出現頻度から符号長の総和(平均符号長)を最小化する木」は同一の最適化構造を持ち、同じ貪欲アルゴリズム(最小の2つを繰り返し結合する)で解ける。この事実は、一見異なる分野の問題が実は同一の数理構造を共有している好例としてよく引用される
- **反例(誤った貪欲戦略)**: 「サイズの大きい2つを先に結合する」「単純に左から順番に結合する」など、最小サイズの2つを選ぶという条件を外れた貪欲的な戦略は、一般には最適解を保証しない。たとえば`{10, 20, 30}`を先頭から順に`(10, 20)`→`(30, 30)`とマージすると総コストは`30 + 60 = 90`だが、最小の2つを優先する正しい貪欲法では`(10, 20)`→`(30, 30)`と同じ結果になる一方、`{10, 10, 10, 50}`のようなケースでは「隣接する2つを順に結合する」方式と「常に最小の2つを選ぶ」方式で総コストが異なり、後者だけが最適値を保証する。「どの2つを選ぶか」という選択基準を誤ると最適性が失われる点が、この貪欲法の正しさの核心である
- **計算量の内訳**: ヒープへの初期投入(ヒープ化)がO(n)、その後n-1回の「取り出し2回・挿入1回」を各O(log n)で繰り返すため、全体でO(n log n)になる。マージ対象のファイル数が数千〜数万に及ぶ外部ソートの現場でも、十分に実用的な速さで最適な結合順序を決定できる
- **外部ソート(External Sorting)への応用**: メモリに収まらない巨大なデータをディスク上でソートする際、複数のソート済みチャンクを段階的にマージしていく必要があるが、その結合順序を最適マージパターンで決めることでディスクI/O(読み書き回数)を最小化できる。チャンクのサイズが不揃いなまま闇雲な順序でマージすると、大きなチャンクが何度も再読み込み・再書き出しされる無駄が生じるため、この貪欲法による結合順序の最適化は実際のディスクI/Oコストに直結する
- **k-wayマージへの一般化**: 一度に3つ以上のファイルを同時にマージできる場合(k-wayマージ)にも、同じ貪欲戦略(常に最小の`k`個を選んで結合する)が拡張できる。ただしこの場合、ファイル数`n`が`(k-1)`で割り切れる形(正確には`(n-1) mod (k-1) = 0`)になっていないと木がいびつになり最適性が崩れるため、サイズ0のダミーファイルを必要数だけ補ってから同じ手続きを適用する、という前処理が必要になる点がハフマン符号化のk分木への一般化と共通している
- **使いどころ**: 外部ソートにおけるチャンクの結合順序決定、複数のログファイル・ソート済みストリームを1つに統合するバッチ処理、分散システムでの部分結果のマージ順序最適化

## 実装例

```python
import heapq


def optimal_merge_cost(file_sizes: list[int]) -> tuple[int, list[tuple[int, int]]]:
    """最小の総マージコストと、実際に行われた各マージのペアを返す。"""
    if len(file_sizes) <= 1:
        return 0, []

    heap = list(file_sizes)
    heapq.heapify(heap)

    total_cost = 0
    merges: list[tuple[int, int]] = []

    while len(heap) > 1:
        a = heapq.heappop(heap)
        b = heapq.heappop(heap)
        merged = a + b
        total_cost += merged
        merges.append((a, b))
        heapq.heappush(heap, merged)

    return total_cost, merges
```

```typescript
class MinHeap {
  private data: number[] = [];

  get size(): number {
    return this.data.length;
  }

  push(value: number): void {
    this.data.push(value);
    let i = this.data.length - 1;
    while (i > 0) {
      const parent = (i - 1) >> 1;
      if (this.data[parent] <= this.data[i]) break;
      [this.data[i], this.data[parent]] = [this.data[parent], this.data[i]];
      i = parent;
    }
  }

  pop(): number {
    const top = this.data[0];
    const last = this.data.pop()!;
    if (this.data.length > 0) {
      this.data[0] = last;
      let i = 0;
      for (;;) {
        const l = 2 * i + 1;
        const r = 2 * i + 2;
        let smallest = i;
        if (l < this.data.length && this.data[l] < this.data[smallest]) smallest = l;
        if (r < this.data.length && this.data[r] < this.data[smallest]) smallest = r;
        if (smallest === i) break;
        [this.data[i], this.data[smallest]] = [this.data[smallest], this.data[i]];
        i = smallest;
      }
    }
    return top;
  }
}

function optimalMergeCost(
  fileSizes: number[],
): { totalCost: number; merges: [number, number][] } {
  if (fileSizes.length <= 1) return { totalCost: 0, merges: [] };

  const heap = new MinHeap();
  for (const size of fileSizes) heap.push(size);

  let totalCost = 0;
  const merges: [number, number][] = [];

  while (heap.size > 1) {
    const a = heap.pop();
    const b = heap.pop();
    const merged = a + b;
    totalCost += merged;
    merges.push([a, b]);
    heap.push(merged);
  }

  return { totalCost, merges };
}
```
