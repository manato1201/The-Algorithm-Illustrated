# 第 0 回 全体の見取り図

> 所要時間の目安: 1 時間 / 前提: TypeScript の基本・配列

## この回のゴール

- アルゴリズムが、**ステップ列(フレームの並び)**になって、画面で再生されるまでを説明できる。
- 「**計算(純粋関数)**」と「**描画(コンポーネント)**」を分ける理由を説明できる。
- 可視化の**正しさを、どう守っているか**を説明できる。

## 1. 流れ

![構成図](../diagrams/architecture.svg)

1. **記事**(`content/algorithms/<id>.md`): 説明・実装例・分類。
2. **ステップ列を作る関数**(`src/lib/*-visualizers.ts`): 入力(固定のデモ配列など)から、**1 コマずつの状態**(フレーム)の配列を作る。**画面にも時刻にも依存しない純粋関数**。
3. **登録表**: `id → 関数` の表。`hasVisualizer(id)` が、「この記事に可視化があるか」を返す。
4. **Web Worker**: ステップ列の生成を、**画面とは別のスレッド**で行う(重い計算で画面が固まらない)。
5. **可視化コンポーネント**: フレームを 1 コマずつ描く。再生・巻き戻し・速度・タイムライン。
6. **検証**(`npm run verify`): ステップ列の**最終結果**が、**独立した計算や既知の正解**と一致するかを、毎回確かめる(1508 件のアサーション)。

## 2. 計算と描画を分ける

| 層 | 場所 | 性質 |
|---|---|---|
| 計算 | `src/lib/*-visualizers.ts` | 純粋関数。**Node だけで動かして検査できる** |
| 描画 | `src/components/visualizer/` | Canvas・HTML・WebGL。**ブラウザが要る** |

計算が純粋なので、**描画なしで、正しさを機械で確かめられる**(`verify`・この講義の例)。描画の見た目は、目で確かめる。

## 3. なぜ「検証」を書くのか

可視化は、**説明と動きが、実際の計算結果と食い違う**と、学習者に**嘘を教える**ことになります。見た目では、食い違いに気づきにくい。そこで、「確認した」と**申告する**のではなく、**再実行できるコード**(`verify-visualizations.mjs`)にして、いつでも誰でも同じ結論に届くようにしています。

## 確認問題

1. ステップ列を作る関数を、純粋関数にしてある利点は何ですか。
2. ステップ列の生成を、Web Worker で行うのは、なぜですか。
3. 可視化の正しさの根拠を、申告ではなくコードにする理由は何ですか。

## 解答

1. 画面なしで、Node だけで動かして検査できる(同じ入力に、同じ出力)。
2. 重い計算を別のスレッドで行い、画面の操作を固まらせないため。
3. 後から誰でも追試でき、変更のたびに食い違いを機械で見つけられるから。

## まとめ

- **記事 → ステップ列(純粋関数)→ 登録表 → Worker → 再生**。
- 計算と描画を分ける。正しさは、**再実行できる検証**で守る。
- 次の回は、**フレーム**の形。
